=  仮想マシンのネットワーク管理

== はじめに

前のセクションで述べたように、すべての仮想マシンはデフォルトで OpenShift ソフトウェア定義ネットワーク（SDN）に接続されており、他の VM や OpenShift ネイティブアプリケーションを含む OpenShift クラスター上の他のワークロードからのアクセスが可能になり、仮想マシンとそれらがホストするアプリケーションをよりモダンなワークフローで管理できます。

* SDN は、クラスター内で VM または Pod としてデプロイされているかにかかわらず、アプリケーションの抽象化、接続、制御された方法での公開に追加機能を提供します。これには OpenShift の *Service* と *Route* 機能が含まれます。
* OpenShift のネットワークポリシーエンジンにより、VM ユーザーまたは管理者は、個々の VM またはプロジェクト/名前空間全体へのネットワークトラフィックを許可または拒否するルールを作成できます。

ただし、必要に応じて、仮想マシンは SDN に加えて、タグなしネットワークや VLAN など、1 つ以上の物理ネットワークに直接接続することも可能です。つまり、管理者は外部 IP アドレスから VM に接続でき、VM は Layer2 ネットワークを使用して直接接続できます。

高レベルでは、Linux ブリッジなどのホストネットワーキングを構成することでこれを行います。本ワークショップセグメントでは、そのプロセスの次のステップである、VM がそのブリッジ、したがって物理ネットワークに直接接続できるようにするネットワークアタッチメント定義の作成を説明します。

NOTE: OpenShift 環境は、仮想マシンが接続する各コンピュートノードに Linux Bridge が既に構成されているため、外部ネットワークリソースとの接続が容易です。

== ネットワークアタッチメント定義の作成

VM で Linux Bridge を使用するには、*Network Attachment Definition* を作成する必要があります。これが OpenShift にネットワークについて伝え、仮想マシンがそれに接続できるようにします。Network Attachment Definition は作成されたプロジェクトにスコープされ、そのプロジェクトにデプロイされた仮想マシンのみがアクセスできます。Network Attachment Definition が *default* プロジェクトで作成されると、グローバルに利用可能になります。これにより、管理者として、独自の VM を管理するアクセス権を持つ特定のユーザーにどのネットワークが利用可能で、利用不可能かを制御できます。

NOTE: ネットワークアタッチメント定義は、OpenShift に既存のネットワークデバイスを利用するよう指示します。本ケースでは、そのデバイスは以前に作成され、*br-flat* という名前です。その名前を使用する必要があります。そうでないと、OpenShift はその特定名のネットワークデバイスを持つノードのみを利用できるため、VM をいずれのコンピュートノードにも配置できません。

== User Defined Networks

ユーザー定義ネットワーク（UDN）の実装以前、OpenShift Container Platform 用 OVN-Kubernetes CNI プラグインは、プライマリまたはメインネットワーク上で Layer 3 トポロジーのみをサポートしていました。Kubernetes の設計原則により: すべてのポッドはメインネットワークに接続され、すべてのポッドは IP アドレスで相互に通信し、ポッド間トラフィックはネットワークポリシーに従って制限されます。新しいネットワークアーキテクチャの学習は、従来の仮想化管理者からしばしば懸念として表明される点です。

UDN の導入により、カスタム Layer 2、Layer 3、localnet ネットワークセグメントを有効にすることで、デフォルトの Layer 3 トポロジーの Kubernetes ポッドネットワークの柔軟性とセグメンテーション機能が向上します。これらのセグメントはすべてデフォルトで分離されています。これらのセグメントは、デフォルトの OVN-Kubernetes CNI プラグインを使用するコンテナポッドおよび仮想マシンのプライマリまたはセカンダリネットワークとして機能します。UDN により、幅広いネットワークアーキテクチャとトポロジーが可能になり、ネットワークの柔軟性、セキュリティ、パフォーマンスが向上します。

クラスター管理者は UDN を使用して、ClusterUserDefinedNetwork カスタムリソース（CR）を活用して、クラスターレベルで複数の名前空間にまたがる追加ネットワークを作成および定義できます。さらに、クラスター管理者またはクラスターユーザーは、UserDefinedNetwork CR を使用して名前空間レベルで追加ネットワークを定義できます。

ユーザー定義ネットワークには次の利点があります:

*セキュリティのための強化されたネットワーク分離* - 名前空間は Red Hat OpenStack Platform（RHOSP）でテナントが分離されるのと同様に、独自の分離されたプライマリネットワークを持つことができます。これにより、テナント間トラフィックのリスクが低減され、セキュリティが向上します。

*ネットワークの柔軟性* - クラスター管理者は、プライマリネットワークを layer 2 または layer 3 ネットワークタイプとして構成できます。これにより、プライマリネットワークにセカンダリネットワークの柔軟性が提供されます。

*簡素化されたネットワーク管理* - ユーザー定義ネットワークでは、ワークロードを異なるネットワークにグループ化することで分離を実現できるため、複雑なネットワークポリシーの必要性が排除されます。

*高度な機能* - ユーザー定義ネットワーキング機能により、管理者は複数の名前空間を単一のネットワークに接続したり、異なる名前空間セット向けに個別のネットワークを作成したりできます。ユーザーは異なる名前空間やクラスター間で IP サブネットを指定して再利用することもでき、一貫したネットワーク環境を提供します。


=== OpenShift Virtualization での User Defined Networks

OpenShift Container Platform Web コンソールまたは CLI を使用して、VM のプライマリインターフェイス上のユーザー定義ネットワーク（UDN）に仮想マシン（VM）を接続できます。プライマリユーザー定義ネットワークは、指定した名前空間のデフォルトポッドネットワークを置き換えます。ポッドネットワークとは異なり、プライマリ UDN はプロジェクトごとに定義でき、各プロジェクトは固有のサブネットとトポロジーを使用できます。

layer 2 トポロジーでは、OVN-Kubernetes がノード間にオーバーレイネットワークを作成します。このオーバーレイネットワークを使用して、追加の物理ネットワークインフラストラクチャを構成することなく、異なるノード上の VM を接続できます。

layer 2 トポロジーでは、ライブマイグレーション中にクラスターノード間で永続的 IP アドレスが保持されるため、Network Address Translation（NAT）なしで VM をシームレスにマイグレーションできます。

プライマリ UDN を実装する前に、次の制限を考慮する必要があります:

. virtctl ssh コマンドを使用して VM への SSH アクセスを構成することはできません。

. oc port-forward コマンドを使用して VM にポートを転送することはできません。

. headless services を使用して VM にアクセスすることはできません。

. readiness および liveness プローブを定義して VM ヘルスチェックを構成することはできません。

NOTE: OpenShift Virtualization は現在、セカンダリユーザー定義ネットワークをサポートしていません。

=== User Defined Networks の操作

. 次の画像に示すように、上部メニューを使用して YAML をインポートできます:

[source,yaml,role=execute,subs="attributes"]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  labels:
    kubevirt.io/vm: fedora-udn
  name: fedora-udn
  namespace: vmexamples-{user}-udn
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        creationTimestamp: null
        name: fedora-udn
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: Always
  template:
    metadata:
      name: fedora-udn
      namespace: vmexamples-{user}-udn
    spec:
      domain:
        devices:
          disks:
          - disk:
              bus: virtio
            name: rootdisk
          - disk:
              bus: virtio
            name: cloudinitdisk
          interfaces:
          - name: primary-udn
            binding:
              name: l2bridge
          rng: {}
        resources:
          requests:
            memory: 2048M
      networks:
      - pod: {}
        name: primary-udn
      terminationGracePeriodSeconds: 0
      volumes:
      - dataVolume:
          name: fedora-udn
        name: rootdisk
      - cloudInitNoCloud:
          userData: |-
            #cloud-config
            user: fedora
            password: fedora
            chpasswd: { expire: False }
        name: cloudinitdisk
----

== まとめ

本モジュールでは、物理ネットワークの操作と Virtual Machines（VM）を既存ネットワークに直接接続することを探りました。VM を物理ネットワークに直接接続することで、管理者は VM に直接アクセスでき、ストレージや管理ネットワークなどの特殊なネットワークへの VM の接続も可能になります。

ユーザー定義ネットワークは、クラスター管理者とエンドユーザーに高度にカスタマイズ可能なネットワーク構成オプションと、プライマリおよびセカンダリネットワークタイプの管理においてはるかに柔軟な体験を提供します。
